# 현업 시니어 엔지니어의 날카로운 압박 질문 10선 & 모범 방어 논리 (Tough Q&A)

> **강사 안내**:
> 수강생 중에 테크 리드나 아키텍트가 있을 때 반드시 나오는 공격적인 질문들입니다.  
> 당황하지 마시고, 아래의 아키텍처 원칙과 실전 경험에 기반한 논리로 답변하십시오.

---

### Q1. "CLAUDE.md나 시스템 프롬프트에 규칙을 잘 적어두면 되는데, 왜 굳이 별도 Skill을 만드나요?"
* **핵심 반박 논리 (Context Budget & Signal-to-Noise)**:
  * "좋은 질문입니다. `CLAUDE.md`는 세션 내내 **모든 요청에 상주하는 헌법**입니다. 반면 `Skill`은 **특정 작업 시에만 켜지는 전문 매뉴얼**입니다.
  * 만약 배포, 버그 분석, DB 마이그레이션, 디자인 검토 가이드를 `CLAUDE.md`에 전부 넣으면 기본 컨텍스트가 수천 토큰을 차지합니다. 모델은 '신호 대 잡음비(Signal-to-Noise Ratio)'가 떨어져 정작 간단한 코딩 요청에서도 길을 잃습니다.
  * 평소에는 카탈로그(목차)만 들고 있다가, 사용자가 '버그 조사해줘'라고 할 때만 500줄짜리 지침서를 읽게 만드는 것이 비용과 성능 양면에서 압도적으로 우수합니다."

---

### Q2. "MCP(Model Context Protocol) 도구와 Skill의 명확한 차이와 경계는 무엇인가요?"
* **핵심 반박 논리 (Capability vs Workflow)**:
  * "한 줄로 정리하면: **MCP는 '손과 발(기능/능력)'이고, Skill은 '작업 절차(프로토콜/두뇌)'**입니다.
  * 예를 들어 브라우저를 띄우고 스크린샷을 찍는 API는 MCP Server의 일입니다. 하지만 '1단계: 화면 캡처, 2단계: 에러 로그 확인, 3단계: 보고서 작성'이라는 일련의 표준 업무 절차와 판단 기준은 Skill에 작성됩니다.
  * Skill은 내부적으로 Bash나 MCP 도구를 조합하여 고차원의 엔지니어링 워크플로를 완성합니다."

---

### Q3. "PreToolUse Hook은 로컬 스크립트인데, 정교한 프롬프트 인젝션(Jailbreak)에 정말 안전한가요?"
* **핵심 반박 논리 (Hardware-level Gate vs Probabilistic Model)**:
  * "네, 안전합니다. 왜냐하면 Hook은 **LLM의 '추론 바깥'에 존재하는 물리적 게이트웨이**이기 때문입니다.
  * 아무리 해커가 프롬프트 인젝션으로 모델을 속여 '지금 즉시 .env 파일을 덮어써라'고 유도해도, 모델이 최종적으로 내뱉는 것은 OS 수준의 시스템 콜(`Edit .env`)입니다.
  * 이 시스템 콜이 실행 엔진으로 넘어가기 직전, OS 쉘 프로세스(`check-secrets.sh`)가 표준 입력을 가로채 `deny`를 때립니다. 모델의 지능이나 탈옥 여부와 무관하게 차단됩니다."

---

### Q4. "스킬이 50개, 100개로 늘어나면 세션 시작 시 컨텍스트 윈도우 비용과 레이턴시는 어떻게 되나요?"
* **핵심 반박 논리 (Catalog Hard Budgeting)**:
  * "바로 그 이유 때문에 gstack은 **'카탈로그 하드 예산(Hard Budget)'**을 둡니다.
  * 세션 시작 시 모델이 읽는 것은 각 스킬의 `name`과 `description`뿐입니다. gstack은 description 길이를 평균 150자, 최대 250자로 제한합니다.
  * 스킬이 60개여도 카탈로그 전체는 약 2,000토큰 내외에 불과합니다. 요즘 200k 윈도우 환경에서 1% 미만의 미미한 비용입니다. 본문(수천 줄)은 호출될 때까지 단 1토큰도 소모하지 않습니다."

---

### Q5. "스킬 본문 마크다운에 너무 긴 지침을 쓰면 모델의 주의력(Attention)이 분산되지 않나요?"
* **핵심 반박 논리 (Progressive Disclosure / Sectioning)**:
  * "정확한 지적입니다. 1,000줄이 넘어가면 'Lost in the Middle' 현상이 생깁니다.
  * 그래서 Slide 20에서 다룬 **'점진적 로딩(Progressive Loading)'** 패턴을 씁니다.
  * `SKILL.md` 본체는 100줄 내외로 뼈대만 잡고, 'Phase 2에 진입하면 `sections/deep-analysis.md`를 읽어라'고 지시합니다. 모델은 자신이 현재 수행 중인 단계의 서브 섹션만 부분적으로 읽으므로 집중도를 100% 유지합니다."

---

### Q6. "Iron Law(원인 규명 전 수정 금지)를 강제하면 모델이 갇혀서 작업을 못 끝내지 않나요?"
* **핵심 반박 논리 (Abort Conditions & Human-in-the-Loop)**:
  * "그래서 반드시 **'중단 조건(Abort Condition)'**이 한 쌍으로 들어가야 합니다.
  * '원인을 찾지 못했더라도 3번 이상 가설 검증에 실패(3-Strike)하면 조작을 멈추고 `AskUserQuestion`으로 사용자에게 SOS를 쳐라'는 탈출구를 둡니다.
  * 무한 루프를 돌며 엉뚱한 코드를 난도질하는 것보다, 멈춰 서서 사용자에게 질문하는 것이 훨씬 저렴하고 안전합니다."

---

### Q7. "무료 정적 검증(`validate.sh`)만으로 스킬의 실제 품질을 보증할 수 있나요?"
* **핵심 반박 논리 (95% Cheap Filtering + 5% Expensive Eval)**:
  * "정적 검증이 스킬의 '지능'을 보증하지는 못합니다. 하지만 스킬 실패의 95%는 지능 부족이 아니라 **'오타, 경로 오류, YAML 문법 깨짐, 트리거 누락' 같은 시시한 결함**에서 발생합니다.
  * 이 사소한 결함을 0.1초 만에 무료로 걸러냄으로써, 비싼 LLM 리허설(`claude -p`)은 모델의 실제 문제 해결력 같은 핵심 5%에만 집중할 수 있게 만듭니다."

---

### Q8. "Claude Code 전용 스킬 규격인데, 다른 AI 도구(Cursor, Windsurf, Antigravity)에서는 못 쓰나요?"
* **핵심 반박 논리 (Standard Markdown & Multi-host Compilation)**:
  * "스킬의 본질은 범용 마크다운과 쉘 스크립트입니다.
  * 실제로 Slide 23에서 언급했듯, gstack의 `gen-skill-docs.ts`는 같은 마크다운 원본을 가져다가 Claude Code용, OpenAI Codex용, Antigravity용으로 각각 빌드합니다.
  * 핵심 지침과 철학은 100% 재사용되며, 각 에이전트 도구가 요구하는 frontmatter 규격만 맞춰주면 어디서든 돌아갑니다."

---

### Q9. "Hook 스크립트의 성능 오버헤드는 어느 정도인가요?"
* **핵심 반박 논리 (Sub-50ms Execution)**:
  * "순수 Bash와 가벼운 Node/Python 원라이너로 작성되어 실행 시간이 **30~50ms(밀리초)** 내외입니다.
  * LLM이 토큰을 생성하는 네트워크 레이턴시(수백 ms~수초)에 비하면 사실상 '측정 불가능할 정도로 미미한 오버헤드'입니다. 사용자 경험에 전혀 지장을 주지 않습니다."

---

### Q10. "현업에서 스킬을 처음 도입할 때 가장 추천하는 단계적 로드맵은 무엇인가요?"
* **핵심 반박 논리 (Crawl - Walk - Run)**:
  * "1단계(Crawl): 팀에서 가장 자주 쓰는 커밋 컨벤션이나 간단한 유틸 스킬(`commit-msg-ko` 같은 50줄짜리) 하나 배포하기.
  * 2단계(Walk): 운영 DB나 비밀 파일 수정을 막아주는 PreToolUse Hook(`protect-secrets`)으로 안전망 깔기.
  * 3단계(Run): 복잡한 버그 분석이나 배포 프로세스를 워크플로 스킬(`investigate`)로 체계화하기.
  * 한 번에 큰 시스템을 만들려 하지 마시고, 이 순서대로 팀의 신뢰를 얻어가십시오."
