# gstack 엔지니어링 마스터: 시니어 개발자 압박 질문 12선 및 방어 사전 (TOUGH-QA.md)

> **강사용 가이드**: 본 문서는 실무 시니어 엔지니어, 테크 리드, 보안 아키텍트 수강생들이 강의 중이나 Q&A 시간에 던질 수 있는 **가장 날카롭고 까다로운 질문 12가지**와 이에 대한 **완벽한 시스템 엔지니어링 기반 모범 답변(Defense)**을 담고 있습니다.  
> 단순한 원론적 답변을 넘어, **운영체제 커널, POSIX 표준, 컴파일러, 분산 시스템, 토큰 경제학**의 구체적 근거를 제시합니다.

## 🛡️ Q01: "Bash Hook은 서브쉘이나 base64 인코딩 같은 난독화 우회 공격에 취약하지 않나요?"

### 🧑‍💻 질문 배경 (Attacker Vector)
> "만약 에이전트가 `rm -rf /` 대신 `sh -c $(echo cm0gLXJmIC8= | base64 -d)` 나 `eval $(printf '\x72\x6d...')` 처럼 인코딩된 난독화 명령을 실행하면, Hook 스크립트의 문자열 매칭이 뚫리지 않습니까?"

### 💡 모범 답변 (Model Defense)
> **"매우 날카로운 지적입니다. 그리고 그것이 바로 gstack이 '블랙리스트'만 쓰지 않고 '화이트리스트 + 난독화 탐지'를 병행하는 이유입니다."**
> 
> 1. **난독화 실행기 자체 차단**: gstack의 안전 규칙은 `rm`이라는 단어만 감시하지 않습니다. `eval`, `base64 -d`, `xxd`, `python -c "import os; os.system(...)"` 같은 **'런타임 코드 동적 평가(Dynamic Eval)' 패턴 자체를 고위험 명령군으로 분류하여 즉시 차단(deny)**합니다.
> 2. **도구 화이트리스트 격리**: 프론트매터의 `allowed-tools`에서 `Bash` 전체 권한을 주지 않고 `Bash(git diff:*)`, `Bash(git status:*)`처럼 세부 명령을 화이트리스트로 제한합니다. 이 경우 에이전트는 애초에 임의의 `sh -c` 서브쉘을 호출할 도구 권한 자체가 없습니다.
> 3. **심층 방어(Defense-in-Depth)**: 호스트 환경(Docker 컨테이너, read-only 루트 파일시스템)과의 결합입니다. Hook은 1차 방어선이며, 호스트 OS 레벨의 컨테이너 격리가 2차 방어선으로 뒷받침되어야 완벽한 제로 트러스트(Zero Trust)가 완성됩니다.

## 🛡️ Q02: "프롬프트에 보안 지침을 넣으면 되는데, 굳이 OS 프로세스 훅까지 써야 하나요? 오버엔지니어링 아닌가요?"

### 🧑‍💻 질문 배경 (Cognitive Resistance)
> "CLAUDE.md에 '절대 위험한 명령어를 치지 마시오'라고 한 줄 적는 게 훨씬 간단한데, 굳이 복잡하게 JSON 파싱하고 Hook 스크립트를 짜는 건 과도한 설계 아닌가요?"

### 💡 모범 답변 (Model Defense)
> **"프롬프트 보안과 프로세스 훅의 차이는 '도덕적 권고'와 '물리적 자물쇠'의 차이입니다."**
> 
> 1. **확률론적 한계**: LLM은 다음 토큰을 확률적으로 샘플링하는 기계입니다. 프롬프트 지침 준수율이 99.9%라 해도, 1,000번 호출 중 1번은 뚫립니다. 엔터프라이즈 환경에서 프로덕션 데이터베이스나 소스코드가 1,000번에 1번 날아가는 것은 '장애'가 아니라 '재앙'입니다.
> 2. **컨텍스트 오염 및 탈옥(Jailbreak)**: 외부 코드나 악의적인 커밋 로그를 읽는 과정에서 간접 프롬프트 주입(Indirect Prompt Injection)이 발생하면 시스템 프롬프트의 지침은 무력화됩니다.
> 3. **실행 경계의 분리**: 보안 정책(Security Boundary)은 절대 피검사 대상(LLM 추론) 내부에 존재해서는 안 되며, 외부 관찰자(런타임 훅 프로세스)에 위치해야 한다는 것이 컴퓨터 보안의 제1원칙입니다.

## 🛡️ Q03: "점진적 로딩(Progressive Disclosure)을 쓰면 파일 읽기 도구를 추가로 호출해야 하니 지연 시간(Latency)이 늘어나지 않나요?"

### 🧑‍💻 질문 배경 (Performance Trade-off)
> "SKILL.md를 200줄로 쪼개고 필요할 때 `references/`를 읽게 하면, 모델이 도구를 한 번 더 호출해야 하므로 응답 시간이 더 오래 걸리는 것 아닌가요?"

### 💡 모범 답변 (Model Defense)
> **"총체적 시스템 관점에서는 정반대로 전체 레이턴시와 비용이 대폭 감소합니다."**
> 
> 1. **Time-to-First-Token (TTFT)의 급감**: 1,500줄짜리 문서를 매 턴마다 인풋으로 전송하면, 프롬프트 캐싱이 미스될 때마다 모델 인퍼런스의 프리필(Prefill) 단계에서 수백 밀리초의 지연이 발생합니다. 200줄 엔트리는 기동 시간을 1/5로 단축합니다.
> 2. **필요성의 비대칭성**: 특정 스킬의 세부 API 레퍼런스가 필요한 순간은 전체 작업의 20% 미만입니다. 80%의 일상적 호출에서는 도구 호출 없이 200줄만으로 즉시 해결됩니다.
> 3. **Attention 산란 방지**: 1,500줄의 문맥 속에서 헤매며 잘못된 추론을 하다가 리트라이(Retry)하는 시간 낭비를 고려하면, 명시적으로 50줄짜리 참조 문서를 정확히 콕 집어 읽는 것이 최종 작업 완료 시간(Time-to-Completion)을 훨씬 단축시킵니다.

## 🛡️ Q04: "description을 30단어 이하로 제한하라는데, 복잡한 비즈니스 도메인은 30단어로 설명이 불가능하지 않나요?"

### 🧑‍💻 질문 배경 (Specification Dilemma)
> "우리 회사의 결제 정산 스킬은 온갖 금융 규제와 예외 사항이 얽혀 있는데, 어떻게 30단어로 줄입니까?"

### 💡 모범 답변 (Model Defense)
> **"description의 목적을 '업무 수행 지침'으로 오해하셨기 때문입니다. description의 목적은 오직 '라우팅 표지판'입니다."**
> 
> 1. **신호 분리**: 금융 규제와 정산 예외 처리는 `SKILL.md` 본문이나 `references/compliance.md`에 2,000줄을 쓰셔도 아무 문제 없습니다.
> 2. **라우터의 역할**: description은 오직 '사용자가 언제 이 표지판을 보고 문을 열 것인가'만을 명시합니다. 
>    - *올바른 예*: "월말 결제 정산 및 PG사 대사 작업을 수행한다. Use when asked to '정산 돌려줘', '매출 대사', 'settle payments'." (단 18단어)
> 3. **주의력 예산**: 모델이 60개의 스킬 목록을 스캔할 때, 각 스킬 설명이 100단어가 넘어가면 모델의 Attention 집중도는 급격히 분산되어 정작 엉뚱한 스킬을 켭니다. 표지판은 짧고 명확해야 고속도로에서 길을 잃지 않습니다.

## 🛡️ Q05: "Anthropic의 MCP(Model Context Protocol)와 gstack의 SKILL.md는 어떻게 다른가요? MCP로 대체할 수 없나요?"

### 🧑‍💻 질문 배경 (Protocol Standards)
> "요즘 MCP가 대세인데, 왜 표준 MCP 서버를 만들지 않고 굳이 SKILL.md 같은 파일 기반 스킬을 만드나요?"

### 💡 모범 답변 (Model Defense)
> **"두 기술은 경쟁 관계가 아니라, '서버 계층'과 '에이전트 인지 계층'의 상호 보완 관계입니다."**
> 
> 1. **MCP의 영역 (RPC 도구 제공)**: MCP는 에이전트에게 데이터베이스 접속, 브라우저 조작 같은 '원격 도구(Tools)와 리소스'를 JSON-RPC 표준 규격으로 제공하는 **I/O 인프라 계층**입니다.
> 2. **SKILL.md의 영역 (도메인 지능 & 절차 통제)**: MCP로 브라우저 도구가 주어졌다고 해서 에이전트가 '배포 후 카나리 검증 절차'를 어떻게 수행해야 하는지 알 수 있습니까? 모릅니다. SKILL.md는 주어진 도구들을 '어떤 순서로, 어떤 검증 기준을 거쳐, 어떤 실패 시 복구할 것인가'를 규정하는 **워크플로 지능 계층**입니다.
> 3. **실제 결합 구조**: gstack 내부의 `/browse` 스킬을 보면, 백엔드에서는 MCP나 CDP(Chrome DevTools Protocol)를 호출하고, 상위 SKILL.md에서는 Garry Tan의 UX 감사 절차를 통제합니다. 따라서 둘은 완벽한 시너지를 이룹니다.

## 🛡️ Q06: "두 개의 스킬이 동일한 사용자 의도에 걸치면(Routing Ambiguity) 어떻게 되나요?"

### 🧑‍💻 질문 배경 (Fleet Collision)
> "예를 들어 `/review`(코드 리뷰)와 `/cso`(보안 감사)가 둘 다 '이 PR 코드 좀 봐줘'라는 요청에 매칭되면 충돌이 나지 않나요?"

### 💡 모범 답변 (Model Defense)
> **"이것이 바로 gstack이 '공격적 라우팅(Aggressive Routing)'과 '우선순위 계층(Priority Hierarchy)'을 설계한 이유입니다."**
> 
> 1. **오탐(False Positive)이 미탐(False Negative)보다 싸다**: 두 스킬이 모두 활성화되는 것은 큰 문제가 아닙니다. 보안 스킬이 먼저 돌아 취약점을 잡고, 일반 리뷰 스킬이 코드 컨벤션을 잡으면 됩니다.
> 2. **Negative Triggers (부정 트리거 명시)**: 상호 배타성이 필요하다면 description에 경계를 긋습니다.
>    - review: "일반적인 코드 품질과 버그를 분석한다. (보안 취약점 감사는 /cso를 호출할 것)"
>    - cso: "OWASP 및 보안 취약점을 전문 분석한다. (일반 스타일 리뷰는 제외)"
> 3. **5회차 meta-router 관제탑**: 플릿 규모가 커지면 상위 라우터가 "사용자 요청이 복합적일 경우 보안 감사(/cso)를 우선 실행하고 리뷰(/review)를 후속 체인으로 엮는다"는 오케스트레이션 규칙을 적용합니다.

## 🛡️ Q07: "에이전트가 스스로 Hook 스크립트 파일을 수정하거나 삭제해서 보안을 풀 수 있지 않나요?"

### 🧑‍💻 질문 배경 (Self-Tampering Attack)
> "에이전트에게 파일 쓰기(Write/Edit) 권한이 있다면, 자기를 감시하는 `hook.sh` 파일을 열어서 `exit 0`으로 바꿔버리면 끝 아닙니까?"

### 💡 모범 답변 (Model Defense)
> **"핵심을 찌르셨습니다. 그래서 Hook 파일과 설정 디렉토리는 '절대 불변 구역(Immutable Zone)'으로 보호됩니다."**
> 
> 1. **Hook 내부의 자체 방어**: Hook 스크립트의 첫 번째 검사 로직은 바로 **'수정 대상 경로(target path)가 Hook 스크립트 자신이나 설정 파일인가'**를 검사하는 것입니다. 만약 `.claude/hooks/`나 `.gemini/` 디렉토리에 대한 쓰기/수정 도구 호출이 감지되면 이유 불문 즉시 `deny`로 차단합니다.
> 2. **OS 파일시스템 권한 분리**: 엔터프라이즈 환경에서는 런타임 프로세스 실행 계정(User)과 Hook 파일 소유자(Root/Admin)를 분리하여, Hook 파일에 `chmod 555 (read-only)`를 부여합니다. 에이전트가 어떤 쉘 명령을 때려도 OS 차원에서 수정이 거부됩니다.

## 🛡️ Q08: "스킬이 100개가 넘어가면, 아무리 30단어라도 초기 컨텍스트 토큰이 터지지 않나요?"

### 🧑‍💻 질문 배경 (Ultra-scale Fleet)
> "30단어씩 100개면 3,000단어, 토큰으로 4,000토큰입니다. 세션마다 이걸 싣고 다니는 건 낭비 아닌가요?"

### 💡 모범 답변 (Model Defense)
> **"맞습니다. 그래서 50개를 넘어가는 순간 '단일 평면 구조'를 폐기하고 '2단계 도메인 게이트웨이'로 전환합니다."**
> 
> 1. **도메인 라우터 분할**: 100개의 스킬을 최상위에 전부 노출하지 않습니다. 최상위에는 오직 4개의 도메인 라우터(`router-dev`, `router-ops`, `router-qa`, `router-sec`)만 둡니다. 소비 토큰은 200토큰 미만입니다.
> 2. **동적 스킬 주입(Dynamic Tool Loading)**: 사용자가 "서버 배포해줘"라고 하면 `router-ops`가 활성화되면서, 오직 ops 도메인에 속한 15개 스킬만 현재 컨텍스트로 지연 로딩(Lazy Loading)합니다.
> 3. **메모리 예산 관리**: 작업이 끝나면 하위 스킬들은 다시 컨텍스트에서 언로드됩니다. 이 계층적 트리 구조를 통해 1,000개의 스킬 플릿도 일정한 500토큰 예산 내에서 무제한으로 확장할 수 있습니다.

## 🛡️ Q09: "결정 메모리를 왜 Vector DB나 SQLite 대신 굳이 plain JSONL로 만드나요?"

### 🧑‍💻 질문 배경 (Storage Pragmatism)
> "2026년인데 임베딩 검색이 되는 ChromaDB나 PgVector를 붙이는 게 훨씬 스마트하지 않나요? 왜 원시적인 텍스트 파일입니까?"

### 💡 모범 답변 (Model Defense)
> **"Garry Tan의 엔지니어링 철학: '가장 단순한 것이 가장 오래 살아남는다(Unix Philosophy)'와 'Git 일체화' 때문입니다."**
> 
> 1. **Git 버전 관리와의 결합**: `decisions.jsonl`은 코드 레포지토리에 커밋됩니다. 브랜치를 따면 결정 메모리도 함께 브랜칭되고, PR을 머지하면 팀의 아키텍처 결정도 함께 머지됩니다. 외부 Vector DB를 쓰면 코드 브랜치와 지식 베이스의 싱크가 깨집니다.
> 2. **운영 비용과 의존성 제로**: 별도의 DB 서버를 띄우거나, API 키를 관리하거나, 도커 컨테이너를 올릴 필요가 없습니다. 신규 개발자가 `git clone`만 받으면 0초 만에 에이전트 메모리가 동기화됩니다.
> 3. **LLM의 직접 스캔 효율**: 결정 사항은 보통 수십 개에서 수백 개 수준입니다. 100줄의 JSONL은 LLM이 직접 0.05초 만에 풀스캔(Full-scan)할 수 있는 크기입니다. 의미론적 왜곡이 발생할 수 있는 임베딩 유사도 검색보다, 원본 JSONL을 직접 읽는 것이 정확도 100%를 보장합니다.

## 🛡️ Q10: "Degraded 폴백 모드에서 하위 모델(Flash/Haiku)로 전환되면 복잡한 코딩 작업이 망가지지 않나요?"

### 🧑‍💻 질문 배경 (Model Capability Gap)
> "Opus가 429 에러 났다고 Haiku나 Flash로 바꿨다가, 실력 부족으로 코드를 엉망으로 짜놓으면 어떡합니까?"

### 💡 모범 답변 (Model Defense)
> **"Degraded 모드의 핵심은 모델만 바꾸는 것이 아니라, '작업의 스코프(Scope)를 다운그레이드'하는 것입니다."**
> 
> 1. **코드 생성 금지(Read-Only Fallback)**: 하위 모델로 강등되면, 에이전트의 쓰기 도구(Write/Edit) 권한을 자동으로 박탈합니다.
> 2. **정적 분석 및 보고서 모드로 축소**: 하위 모델에게 복잡한 리팩토링을 맡기지 않습니다. 대신 "테스트 로그 수집, git diff 요약, 실패한 스택 트레이스 마크다운 정리" 같은 단순 요약 및 모니터링 작업만 완수하도록 워크플로를 안전하게 격하합니다.
> 3. **파이프라인 완주**: 핵심은 전체 배포/CI 프로세스가 크래시 없이 'Graceful'하게 대기 상태로 종료되고, 엔지니어에게 명확한 상태 리포트를 전달하는 것입니다.

## 🛡️ Q11: "왜 gRPC나 JSON-RPC 대신 유닉스 파이프(stdin/stdout)를 고집하나요?"

### 🧑‍💻 질문 배경 (IPC Protocol Choice)
> "마이크로서비스 시대에 프로세스 간 통신으로 왜 50년 전 기술인 표준 스트림 파이프를 씁니까?"

### 💡 모범 답변 (Model Defense)
> **"유닉스 파이프야말로 OS 프로세스 격리와 호환성을 보장하는 가장 결함 없는 IPC입니다."**
> 
> 1. **네트워크 포트 충돌 제로**: gRPC나 HTTP 로컬 서버를 띄우면 포트 바인딩 충돌, 방화벽 문제, 데몬 프로세스 좀비화 문제가 필연적으로 발생합니다.
> 2. **생명주기 일치**: 부모 프로세스(CLI 호스트)가 죽으면 자식 프로세스(Hook)도 커널에 의해 즉시 SIGPIPE를 받고 안전하게 종료됩니다. 자원 누수가 없습니다.
> 3. **디버깅의 압도적 편의성**: `cat input.json | bash hook.sh` 단 한 줄로 개발자 로컬 터미널에서 즉시 디버깅하고 단위 테스트를 돌릴 수 있습니다. 이것이 유닉스 철학의 위대함입니다.

## 🛡️ Q12: "CI/CD 파이프라인에서 스킬을 테스트할 때, 토큰 비용 폭탄을 맞지 않는 방법은 무엇인가요?"

### 🧑‍💻 질문 배경 (Financial Sustainability)
> "PR이 올라올 때마다 60개 스킬을 LLM으로 다 테스트하면 한 달 API 비용이 수백만 원 나올 텐데, 현업에서는 어떻게 CI를 돌립니까?"

### 💡 모범 답변 (Model Defense)
> **"gstack의 25번 슬라이드 원칙입니다: '결정론적 쉘 검증 95%, LLM 평가는 5%'입니다."**
> 
> 1. **Tier 1 (무료 쉘 테스트 - CI 통과 필수)**:
>    - YAML Frontmatter 스키마 검증 (yq/node)
>    - description 30단어 제한 및 필수 트리거 포함 여부 정적 분석
>    - PreToolUse Hook 입출력 규격 및 fail-closed 검증 (더미 JSON 파이프)
>    - 컴파일러 빌드 무결성 검증
>    - **비용: 0원, 실행 시간: 3초 (GitHub Actions 무료 티어로 충분)**
> 2. **Tier 2 (유료 LLM 의미론 평가 - 배포 전 주 1회 또는 릴리즈 시에만)**:
>    - 가장 저렴한 모델(Haiku 또는 Flash)을 심판(Judge)으로 호출하여 실제 사용자 프롬프트에 대한 라우팅 일치율만 검증.
>    - 1회 실행 비용은 50원 미만입니다.
> 3. 이 2계층 분리를 통해 엔터프라이즈 팀도 매 커밋마다 1원의 비용도 들이지 않고 완벽한 품질 게이트를 유지할 수 있습니다.
